# API contract: authentication, orders, funds, and change reservation

> Historical Phase 0 design contract. The checked-in Candid files and later phase reports describe the current implementation.

- Basis: `Implementation.md` 2.3, Chapter 5, Chapter 7, Chapter 11, Chapter 14.3, `Plan.md` 16.1~16.5
- Status: Design contract. Candid extracted from implementation will be fixed to `candid/`. The deployment contracts for testnet and mainnet are undecided.

## 1. Scope of application and common terms and conditions

- All APIs for the user require a session with revocation generation (`SessionHandle`) and an HPKE encryption envelope (5 sections). Even for queries, owner authorization is not omitted.
- The `caller` equivalent field in the input is not trusted. The caller is obtained from the IC message.
- Each update is responded to after the reception is confirmed as a synchronous transaction. Reception does not mean acceptance or fill in HL (Section 2 of `state-machines.md`).
- Do not hold a database transaction across external calls (`sign_with_ecdsa`, HTTPS outcalls, or `/info` reconciliation). Follow the order in `Implementation.md` 2.3.
- The response does not include data from other users, plaintext order text, signing payload, or HPKE private key.
- All numbers are represented as integers (`money-and-units.md`). Does not accept floating-point and exponent notation.


- Agent generation is requested by `request_agent_generation`. `funds_vault` generates the account's master public key and a random `account_id` and binds it to the identity ID. It does not allow users to declare any HL account address or Agent address (Chapter 7 of Implementation.md).
- Approval is executed by `funds_vault` signing and executing with `trading account master` and `approveAgent`, and then makes it `active` after independently reconciling the approval status of HL. Requests where registered `trading_core` caller, account, generation, and derivation public key do not match are rejected.
- Prohibit the reuse of revocation generation. Stopping or unstopping is performed by Canister, and it does not guarantee the direct unstopping of the user's HL.
- If you want to enable the builder fee, you must request `approveBuilderFee` separately, which is not required for Agent approval (Phase 3-6).

- The sending of funds action and the periodic reconciliation of deposits are launched in the real world by the global timer (`ic-cdk-timers` with `set_timer_interval` of 5 seconds intervals. Rearm with `init`/`post_upgrade`). Heartbeat is not used (it is called every round even without messages, and the cost is also incurred during idle time). Persisted state (actions and ledger entries) is authoritative; correctness does not depend on the timer running continuously (failures are retried in the next launch, and `trading_core` can be restarted even with manual `sweep`).

## 3. trading_core

### 3.1 Order

```candid
type OrderKind = variant { market_ioc; limit_gtc };
type Side = variant { buy; sell };

type SubmitOrderArgs = record {
  client_request_id : RequestId;
  account_id : Blob32;
  market : variant { btc_perp; eth_perp };
  side : Side;
  kind : OrderKind;
  quantity : text;               // Normalized decimal string
  limit_price : opt text;        // market_ioc is mandatory (IOC limit orders with slippage limit)
  slippage_tolerance_bps : opt nat32; // market standard 50bps (0.5%)
  reduce_only : bool;
  leverage : opt nat32;          // Default 3, maximum 5
  trigger : opt record { kind : variant { stop_loss; take_profit }; trigger_price : text; is_market : bool };
  expires_after : opt Timestamp;
};

type SubmitOrderResult = record {
  request_id : RequestId;
  order_id : Blob32;
  cloid : Cloid;
  accepted_state : variant { queued };
  accepted_at : Timestamp;
};

type CancelOrderArgs = record { client_request_id : RequestId; order_id : Blob32; };
type CancelAllArgs = record {
  client_request_id : RequestId;
  market : opt variant { btc_perp; eth_perp };
  include_protective_orders : bool;   // true requires the confirmation screen
};

type CloseAllOutcome = record {
  submitted : vec SubmitOrderResult;
  failed : vec record { market : text; error : ErrorCode };
};
```

- `trigger` can only be accepted as `positionTpsl` (`reduce_only` required) in terms of positions. When the positions exist and `side` indicates the opposite trading of those positions, it is checked at the time of acceptance. The upward and downward movements relative to the market price (the SL for long positions is below and the TP for long positions is above) are not checked at the time of acceptance because the core does not have a mark price, and are left to the exchange's judgment.
- `close` (partial/full settlement) is sent as a reduce-only order for opposite trades. `close_position` is sent for one item with a specified ratio (bps), and `close_all` is repeated for each position (it does not stop the entire position after one failure, but returns the results for each stock). The settlement quantity is rounded down to `szDecimals` by multiplying the number of positions by the ratio. The price is determined by the slippage limit set by the market on the screen (when omitted, it approximates the mark price from the observed positions).
- `reduce_only` is excluded from the scope of risk reservation and trading exchange data freshness gate because it does not increase new risks. Emergency suspension stops accepting new orders regardless of the type of operation (no settlement is accepted during suspension).
- Do not combine Cancel All and positions settlement into the same operation. If Cancel All also deletes the protective SL/TP, request the `include_protective_orders = true` shown in the UI.
- Market is built as an IOC limit order with HL slippage limit. Do not treat it as an order remaining on the board.
- `expires_after` is the acceptance deadline for action, not the cancellation deadline for orders that remain on the board (section 4 of `state-machines.md`).
- There are two signature methods. trading action (order/cancel/cancelByCloid/updateLeverage) uses the phantom agent method (EIP-712 domain `Exchange`／`1`／`1337`／`0x0`), while fund and account operations (`approveAgent`, `usdSend`) use user-signed EIP-712 (domain `HyperliquidSignTransaction`／version `1`／chainId is the `signatureChainId` of the action). On 2026-09-19, the official SDK fixture was verified to match (`docs/phase-1/README.md` section 6). Agent approval is handled by `funds_vault` using the master key, and `trading_core` does not (`authority-matrix.md` section 4).

### 3.3 Send and reconciliation (sweep)

Acceptance (`submit_order`, `cancel_order`, `cancel_all`, `close_position`, `close_all`) only confirms the local state, while signature, transmission, and reconciliation are handled by `sweep`. The production runs with the global timer (`ic-cdk-timers` `set_timer_interval`) starting every 5 seconds (timers are lost during upgrades, so they are rearmed with `init`/`post_upgrade`), and manual execution during shutdown is called by `sweep` (only the controller). Heartbeats are not used (they are called every round even without messages, and they also incur cost during idle time).

- Maximum per transaction: 4 sends, 4 cancellations, 2 accounts, 4 order statuses per account (to reduce the number of outcall transactions).
- The send (`/exchange`) is a **non-replicated** POST. In addition to interpreting the `ok` status from outside HTTP, it also interprets each status. Acceptance is `open` or immediate `filled`, explicit rejection is `rejected` plus release of risk reservation, and unknown outcome is `unknown` and **does not resend** (does not release risk reservation either. Resolution is carried out through reconciliation or confirmed operations by the controller).
- reconciliation (`/info`) is performed using the **replicated** outcall + transformation function (`transform_info`) in fee scheme v2. fill (`userFillsByTime`) is incorporated into the ledger idempotently using `tid`, positions (`clearinghouseState`) is replaced with the **total quantity of observations**, and order status (`orderStatus`) is reflected only in non-terminal orders where the oid is known. Although the replication process cannot eliminate any false or missing history from the HL itself, the reliability conditions of external traces and the completeness of the history are separately verified.
- The target for reconciliation is valid accounts that have trading exchange addresses saved in `accounts`, and they are traversed by a cursor in order of `account_id` (do not limit to the first N items). The address is obtained and saved from the vault only once during the processing of the signature-verified requests of the owner.
- Automatic sweep (timer) is only built for production builds. In test builds, the same path is driven with a explicit `test_sweep_now` (so it can't be confused with the outcall where the test waits in PocketIC).

## 6. HPKE envelope and the route of personal data

Based on `Plan.md` 16.5 and `Implementation.md` 6.1 and 6.3.

```candid
type HpkeRequest = record {
  key_id : blob;                 // ID of the server's public key
  network : Network;
  canister : principal;
  method : text;
  request_id : Blob32;
  expires_at : Timestamp;
  client_public_key : blob;      // Browser public key that encrypts the response
  aad : blob;                    // network/canister/method/caller/request_id/binding the expiration date
  ciphertext : blob;             // ChaCha20-Poly1305
};

type HpkeResponse = record {
  request_id : Blob32;
  key_id : blob;
  observed_at : Timestamp;
  ciphertext: blob;             // for client_public_key
};
```

- The scheme is RFC 9180 HPKE (X25519 / HKDF-SHA256 / ChaCha20-Poly1305). Using audited implementations, do not create primitives from scratch. The implementation uses a shared crate `crates/hpke-envelope` (used by `funds_vault` and `trading_core`).
- `key_id` is the actual public key of the current generation (32 bytes). The key is generated using `rotate_hpke_key` (only for controllers), and the envelope of the retired generation is not decrypted (the client retrieves the public key again).
- The public key, key ID, and expiration date are obtained as an authenticated response from IC and are verified by the client.
- The authentication target will refuse to reuse in different environments and different purposes, including `network`, `canister`, `method`, `caller`, `request_id`, and expiration date. The server will recompute `aad` to confirm consistency and use the same value for decryption (tampering will result in decryption failure).
- HPKE is not a substitute for identity authentication or resend prevention. We perform session verification and `request_id` verification separately. `request_id` is recorded as a one-time use for requests that have successfully been decrypted and is used to reject resend (`BadRequest.NonceReused`). The records are purged when expired, but observation data used for reconciliation (such as positions and fill) is not discarded just because the expiration date has passed.
- The request deadline is limited to 300 seconds from `now`. expired will be rejected with `BadRequest.ExpiredIntent`.
- The scope is `get_account_snapshot`, `list_orders`, `list_fills`, `cancel_order`. The scope for `submit_order`, `cancel_all`, `close_position`, `close_all`, `request_agent_generation`, and `get_agent_status` is not performed (judged in Phase 3).
- Do not permanently store session key and personal cache in the browser (do not use `localStorage`, `IndexedDB`, or cookies).
- HL direct connection in the browser will only be through the public market channel. User-related WS/REST, Agent approval, trading account reconciliation will not be sent from the browser to HL.

|---|---|---|
| You can retry with the same `client_request_id` and the same content. | `UpstreamUnavailable`, `VenueRateLimited`, `SigningQueueFull` | Resend with the same idempotent key. Do not create a new cloid or nonce. |
| You can retry after updating the status. | `StaleAccountState`, `PolicyUnavailable`, `ReservationConflict` | Re-obtain the state, update `revision` and `observed_at`, then re-evaluate |
| Retry after each reception | `JournalWriterBusy` | Temporary contention for a single write fence. `open_session` will retry with a new challenge and signature, with bounded retries, because the previous challenge has already been consumed. Other requests will follow the idempotency rules of each request. |
| Cannot retry | `Unauthenticated`, `SessionExpired`, `SessionRevoked`, `NotEligible`, `BadRequest`, `IdempotencyConflict`, `InsufficientFunds`, `RiskLimitExceeded`, `NotAllowed`, `Internal` | Display the reason and correct the input. Do not automatically resend (`Internal` is a permanent error that includes configuration errors and DB inconsistencies) |
| Successful treatment (duplicate acceptance) | `DuplicateIgnored` | Display the existing reception status. Do not display error |
| Automatic resend prohibited (only reconciliation) | `UnknownPending` | Display as unknown outcome and do not resubmit until the reconciliation result is received. |
| Top-level rejection | `UpstreamRejected` | Follow `retryable`. `retryable = false` revises input and risk. |

- `IdempotencyConflict` occurs when the content is different with the same `client_request_id`. Resending the same content returns the result of the accepted result (`money-and-units.md` section 4).
- Do not include other users' balance, orders, and account addresses in error responses.
