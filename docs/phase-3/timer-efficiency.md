# タイマー効率の調査（2026-09-29）

対象は未デプロイの単一Canister実装。HTTP outcall v2 / non-replicatedは維持する。

## 今回の修正

Vault/Coreとも、DB更新後にタイマーが停止中なら未処理仕事の存在を確認してから起動する。Cyclesサンプルやセッション・HPKE関連の書き込みだけでは空のタイマーを作らない。DBの読み取り失敗時は従来どおり起動し、仕事の放置を防ぐ。動作中のタイマーには変更せず、停止直前の再確認も維持する。

DB接続を解放した後のコールバックから読み取りだけを行う。コールバック内で書き込むと再帰するため禁止。公開API・永続スキーマの変更はない。

## 共通タイマーの考え方

単に二つの5秒タイマーを一つにして順番にawaitすると、資金のHTTP待ちが取消・注文の処理を遅らせる。共通化するなら「次回実行時刻・件数上限・再試行間隔」の設定と予約管理を共有し、Vault/Coreの実行状態は独立させる。

まず各仕事にnext_dueを定義し、実行可能な仕事がなければ最短期限まで眠る構成が有効。タイマー本数だけ減らしてもHTTP回数は減らない。長い外部通信を待つ共通dispatcher一つに集約する変更は行っていない。

## 削除しない処理

未確定送信の照合、注文終了後の最終口座・約定確認、建玉がある口座の監視、送金結果の台帳反映、復旧フェンス解除は必要。UIを閉じても必要な処理を完了できること、結果不明の送信を再送しないことを優先する。
