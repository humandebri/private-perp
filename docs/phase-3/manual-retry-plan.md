# 手動再試行の実装範囲

状態: 資金・注文・通常監視の実装とローカル検証を実施。未デプロイ。後方互換不要の承認に基づき、旧版回収の移行経路は削除。

## 変更する動作

- 送信前に失敗した資金移動・注文・取消は、自動処理の対象から外す。予約を勝手に解放しない。
- 送信後に結果不明となった操作は、自動照合も停止する。ユーザーには「結果を確認」を提供し、再送は提供しない。
- 通常の建玉・注文監視は維持する。ただし通信失敗した監視単位は停止し、手動の「監視を再開」で再開する。他口座の監視には影響させない。
- 結果保存・復旧フェンス解除の失敗も、失敗した操作単位で停止する。正常な後続処理は継続する。
- UIの通常の情報更新、入金確認、新規注文受付は停止解除の契機にしない。

## 永続化と競合の扱い

自動処理の許可は業務状態から独立した永続レコードで管理する。操作ID・処理段階・所有者・世代・実行許可を保持する。実行中の二重操作はスコープ別のガードで拒否し、永続許可はawait前に消費する。送信状態、署名、payload、nonce、残高、予約、証跡を「再試行のため」に巻き戻さない。

手動操作はセッションを検証し、操作の所有者をDBで確認してから一度分の実行許可を与える。実行中は二重クリックを含む並行要求を拒否する。許可を消費してからawaitし、失敗・trap・upgradeで同じ許可が再利用されないようにする。タイマーは実行可能な許可・通常監視のみで起動する。

送信前の再試行は、外部POST未実行と証明できる段階のみ既存の安全確認を経て実行する。レバレッジ設定などの事前POSTも区別する。結果不明の場合は履歴・注文状態の照合だけを行い、残高や予約の確定には既存の証跡検証を使う。一度で判明しない場合は停止状態を保持する。

## 変更箇所

- db: Vault/Coreの追加マイグレーション、実行許可の取得・消費・停止と対象抽出。
- funds-vault: outbox送信、結果保存、照合、着金確認、フェンス解除の処理段階ごとの停止。暗号化private APIに所有者用の再試行・結果確認を追加。
- trading-core: 注文・取消の送信前失敗、結果不明、監視失敗を区別。暗号化private APIで所有者の操作だけ再開。
- frontend: 自動再試行を削除し、停止中の操作と「一度だけ再試行・結果確認」「監視を再開」を表示。通常refreshはこれらのAPIを呼ばない。

## 必須検証

1. 外部エラー後に時刻を進めても同じPOST・照合を自動発行しない。
2. 送信前の失敗のみ手動で一度再試行できる。
3. 結果不明は手動操作後もPOSTを再送しない。
4. 別ユーザー・失効セッションからの再開を拒否する。
5. 二重クリック・実行中の再開・await後の競合で重複送信しない。
6. upgrade後も停止が維持され、結果不明をqueuedへ戻さない。
7. 成功している他口座の建玉・注文監視は継続する。
8. 未解決操作だけが残る場合はタイマーが停止し、UIの通常refreshでは再開しない。

ローカルコードとテストのみを変更対象とし、公開Canisterの操作、デプロイ、資金移動は含めない。

## 実装した契約

Vault/Coreの暗号化private APIに `get_manual_work(SessionHandle)` と `resume_manual_work(SessionHandle, kind, work_id, generation)` を追加。停止一覧は最大100件で所有者だけに返し、完了済み・実行中は除外する。表示された世代の許可は一度だけ付与でき、実行中・古い世代・別の所有者の要求は拒否する。

`worker_permissions` は送信・残高テーブルから独立しており、upgradeで保持する。送金のコールバック消失は手動許可後に既存のCASでdispatchingからunknownへ進めて照合する。queuedへの巻き戻しや署名・nonceの消去はしない。結果保存、フェンス解除、口座監視はそれぞれ独立した許可を使う。

## 残っている制限

旧版の未解決回収の引き継ぎは非対応。`sync_legacy`、旧版移行API、全体移行ロックを削除した。現行の口座別回収フェンス・送信記録・結果不明の再送禁止は維持する。新規インストールと現行版同士の状態保持を対象に検証する。

結果が未確定である限り、予約や復旧フェンスを維持する。手動操作は結果を確定できる保証ではなく、一度の再試行・照合許可。ブラウザの表示更新は継続するが、停止したバックエンド処理の再開許可にはならない。

## ローカル検証（2026-09-29）

- PocketIC: 注文・取消13件、送金outbox16件、資金回収15件、vault照合1件を検証。取消応答消失後は自動でorderStatusを取得せず、手動許可で一度だけ取得し、未解決なら再び停止するケースを含む。
- 単一Canister: production/test-venueの市場取得4件と統合1件、および旧公開Wasmからのアップグレードを検証。停止許可の永続化、別ユーザー拒否、実行中・古い世代の拒否、停止時のHTTP停止を含む。
- Rust: Wasm向けClippy（warningsをエラー扱い）、fmt、トランザクション内await禁止チェック、diff whitespaceチェックを実施。
- Frontend: 型検査、lint、単体45件、build、ブラウザ3件成功。実Canisterとの認証付きブラウザフロー1件は環境未設定でskip。vlmkitの表示・操作検査は成功したが、無効化されたボタンや未実行イベントの警告は残る。
- 公開Canisterの起動・デプロイ・送金は実行していない。旧版の未解決回収の引き継ぎは対象外。

## 旧版互換経路の削除後の確認

`sync_legacy` と移行用4 API、全体移行ロックを削除し、Candid・生成バインディングを更新した。統合Wasmの112メソッドとCandidが一致することを確認。単一Canisterのproduction/mock各5テスト、注文13テストを再実行して成功。回収テストは旧版移行確認を現行フェンスのupgrade保持・他者による解除拒否・正規解除・旧API不在の確認へ置き換えた。Rust Clippy、fmt、トランザクション境界チェック、フロントエンド型検査も成功。

## 再開不能状態の扱い

レバレッジ事前設定が `unknown` の注文と `recovery_ambiguous=1` の資金移動は、通常の手動再開を拒否する。所有者・世代・停止状態の検証後、許可更新と同じトランザクション内で判定し、拒否理由を暗号化APIで返す。停止行と世代は保持するためUIから消えない。前者は管理者による既存の結果解決が必要で、後者は証跡調査が必要。再開のための予約解放・証跡リセットは行わない。
