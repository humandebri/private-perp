## 設計上の矛盾（Agent鍵の所在。注文パイプライン着手前に確定が必要）

現状の実装では**vaultが**Agent鍵を導出・保管し（`agent_generations.agent_address`はvaultの
tECDSAから導出）、vaultがmaster鍵で`approveAgent`を署名している。一方 `Implementation.md` 7章は
「coreが口座別・世代別のAgent鍵を導出・保管し、vaultはmaster署名でそのアドレスを承認する」と
しており、coreの実装にも「vaultへ任意digest署名を要求する経路を追加しない」と明記している。

このままでは、注文署名に必要なAgent秘密鍵がvaultにしか無く、coreは注文を署名できない。
選択肢は次の2つ。

1. **（推奨）coreがAgent鍵を導出・保管**し、vaultの `approve_agent_generation` は
   *agent address（20バイト）を受け取って* master鍵で承認する。vaultは注文内容を知らない。
2. vaultが注文payloadの署名APIを提供する。ただし「任意digest署名の禁止」（authority-matrix 5節）に
   抵触するため、金額・市場・宛先をvaultが検証できる形に限定する必要があり、責務が崩れる。

**1を採用して責務を移した（2026-09-20）**：
- `trading_core` がAgent鍵を導出・保管し（coreスキーマ `agent_generations` v4、`request_agent_generation`／`get_agent_status`）、
- `funds_vault` の `approve_agent_generation` は**渡されたアドレス（20バイト）をmaster署名で承認**して送信し、受理時のみ帳簿を`active`へ遷移させる（PocketICで受理・拒否の両方を検証）。

整理は完了した：vault側の旧 `request_agent_generation`／`get_agent_status`（vault自身が鍵を導出する重複経路）を削除し、鍵は `trading_core` のみが導出・保管する。次は注文パイプライン（Agent鍵での署名・非replicated送信・`orderStatus`照合）に着手する。
